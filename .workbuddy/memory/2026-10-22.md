### 五、~~`--kv q8_0` 有缺陷~~ **【已作废——见本节末尾的引擎内自检：q8_0 与 int8 误差相同，缺陷结论不成立】**

- **反常**：q8_0 每 **32** 值一个 scale（更细），int8 每 **64** 值一个（更粗），结果 **int8 追平 fp16（2 脏），q8_0 反而更差（3 脏）**。更细的 scale 在数学上不可能更差 ⇒ **kvm==4 分支有缺陷**，不是"精度不够"。字节数还更贵：q8_0 每 cell 272 B > int8 264 B（`kv_half_bytes`，HD=256）——**又贵又差，被 int8 严格支配**。
- **为什么单测没抓到**：`kv_q8_parity.exe` 通过（"worst INT8-vs-FP16 error 0.587 quantization steps"），但它测的是 `include/strata/kernels/kv_q8.hpp`（主线档），**完全没覆盖 q36 引擎内联的 kvm==4 块**。kvm==4 的三个消费者我都读过并认为索引自洽（写 [:419-432](src/qwen35/q36_engine.cu#L419-L432)/[:454-468](src/qwen35/q36_engine.cu#L454-L468)，读 [:555-562](src/qwen35/q36_engine.cu#L555-L562)/[:575-580](src/qwen35/q36_engine.cu#L575-L580)，fp16 副本 [:705-723](src/qwen35/q36_engine.cu#L705-L723)）——静态读码不足以定位，需要**端到端模式对拍**。
- **Hadamard 旋转与本 bug 无关（我一度以为是，错了）**：`STRATA_KV_ROT=1`（[generate.cpp:3021](src/program/generate.cpp#L3021)）和 `st.kv_rot`（[layer.cpp:808](src/core/layer.cpp#L808)）是**主线 QSA 路径**的东西；`grep -i 'hadamard|kv_rot|fwht' src/qwen35/` **零命中**——q36 引擎任何 KV 档都没有旋转。所以 int8（干净）与 q8_0（脏）**都未旋转**，"缺旋转"解释不了这个反差；**缺陷就是 kvm==4 自身的路径**。旋转仍是 q4_0/k8v4 那两档（同样 3 脏）可用的改进手段，但是另一件事。
### 六、可部署的处置

### 二、"q8_0 有缺陷"是我误判，引擎内自检已推翻（测具本身要带对照组）
`k_kv_check`（[q36_engine.cu:743](src/qwen35/q36_engine.cu#L743)）+ `STRATA_Q36_KV_SELFCHECK=1`：同输入用同一个 `k_attn_prep` 跑两遍，`kvm=0` 存 F32 当真值，再用**引擎自己的读取表达式**读回。fp16 档 **worst |err| = 0**（对照组，证明测具准）。int8 **0.0536**、q8_0 **0.0533**（均为 |K|max 13.82 的 0.39% = int8 理论步长 1/(2*127)）、q4_0 **0.84**（6.1% = 4-bit 应有量级，半格 13.82/7.5/2 约 0.92）、k8v4 0.154（受 V 限制）。逐 `dim%32` 平坦 ⇒ **五档读写全部正确**。
我犯的两个测具 bug（都记下来）：① 一开始 `k_kv_check` 漏了 `kvm==2` 分支，q4_0 掉进 F32 兜底被当 float 读，得出荒谬的 `4.7e+37`；② 直接跑引擎时它打印的是 **id 序列**（`gen: 760 1156 ...`），我的解码分支没剥掉 `gen:` 前缀，导致 5 条用例被误判全脏。另外 k8v4 是 **INT8-K + Q4_0-V**，K/V 两侧的档必须分开处理。

### 三、A/B 那两案（保留 BF16 dense vs 让引擎吃原版）用引擎原话判死
- 从 A 造 `q36v2`（router squeeze 41 + shexp NVFP4→Q8_0 120 + **dense 保留 BF16 202**，`_tmp_code/make_q36_v2.py`）→ 加载即拒：`strata-q36: blk.0.attn_qkv.weight is BF16, which the native MMVQ does not take`。
- 白名单 [native_mmvq.cu:2887-2892](src/kernels/cuda/native_mmvq.cu#L2887-L2892) 按 block 字节数反解：8=Q8_0(34/32)、20=Q4_0(18/32)、6=Q5_0、11/12/13/14=Q3_K/Q4_K/Q5_K/**Q6_K**(110/144/176/210 per 256)、23=IQ4_XS、42=18/64、16/17/18/21/22/29=IQ 族。**没有 F32/F16/BF16** ⇒ **Q8_0 已是该 dense 路径能加载的最高精度**，生产的 q36 已在使用；"q36_v2 保 BF16"需要新内核（`native_bf16_mmvq` + `native_nvfp4_mmvq`，NVFP4=40 同样不在名单），不是 loader 改改就行。
- 原版 A 直接加载也被拒，第一条原因是形状：`blk.0.ffn_gate_inp_shexp.weight is [2048, 1], the Qwen3.6-35B-A3B layout wants [2048]`（squeeze 可离线做，`fix_router_shape.py` 就干这个；做完立刻撞上面的 BF16 dense）。
- 三轴实测：q4_0 在 262K 下比 q8_0 多 **1.37 GiB**，但换成常驻专家（48→64 slots）**反而变慢**（pp 865→804-818，tg 49.3→47.7-48.6），80 slots 装不下；pp/tg 四档全平 ⇒ **KV 档买的是显存不是速度**。逐 cell 每 KV head：fp16 2048 B / int8 528 / **q8_0 544（比 int8 还贵 1.5%）** / q4_0 288。生产保持 `--kv q8_0`（中途改 int8 又改回，理由已作废）。

## 2026-10-23 续：畸形工具调用泄漏的服务器侧修复

**症状**（用户 14:38 截图）：一条真实发射 `<tool> <parameter name="glob"> …</function> </tool_call>` 以原文出现在聊天窗口，`tool_calls` 为空。

**根因（实测，非读码推测）**：该发射偏离模板两处——包装标签丢了 `_call` 写成 `<tool>`；工具名写在属性里（`<parameter name="glob">`）而非模板的 `=glob`。后者**第 11 个字符是空格而非 `=`**，`startswith("<parameter>=")` 为假，`_follower` 直接判成 text；更糟的是它在标签**尚未闭合**时就被判定，`after.find(">")` 返回 -1，切片 `after[0:]` 把属性标签复制进正文，于是流式 args 流出空对象而最终 arguments 正确（客户端拼增量，看到的仍是空调用）。

1. `_follower` 认两种参数标签写法（`PARAM_TAG`、`PARAM_OPEN_RE`），并在标签闭合前返回 wait，与模板 `=` 形式同等待遇；
2. 属性形式在**调用方**归一化，切点用标签自己的闭合 `>`，未闭合不改写；
